# M2 - Map editor plugin: building placement

## Where we are (branch feature/map-editor-plugin)

IMPLEMENTED (see git log "Add building placement mode (M2)"): suite green
472/472, smoke OK, golden OK, zero SCRIPT ERRORs. The interactive palette/
click layer is user-in-the-loop verified (remote machine): the acceptance
gate stays open until then. Validator needed NO changes — placement emits
exactly the conventions it already checks.

## Placement bugfixes (user-remote testing, 2026-11-21)

1. **Metadata must key off the building KIND, not the minted node name.**
   The scaffold already owns "tower" under each team, so user placements
   are minted "tower_2"; matching apply_building_meta on the minted name
   made every second+ castle/barrack/tower/church placement silently
   neutral — "the blue/red toggle doesn't set the team". The plugin now
   passes the scene base name; pinned by test_building_logic.
2. **Neutral is an explicit dock choice** (blue/red/neutral). Neutral
   placements host under buildings/blue (else red; else dock error — the
   validator only allows blue/red children under 'buildings') with
   team = "neutral". castle/barrack/tower refuse neutral
   (is_placement_allowed; validator fails them and the win condition
   needs buildings/<team>/castle).
3. Team-color editor preview: see below (applies to neutral placements
   too via building.team).

## Team-ownership convention (learned from three_lane_map.tscn, 2026-11)

- castle, barrack, tower: team = directory, subtype = lane (validator-
  enforced; validator calls these _TEAM_STRUCTURE_NAMES).
- **church: team = directory, subtype = backwood** — the red church carries
  team = "red" in the shipping map, so it is team-OWNED even though the
  validator's structure list doesn't include it (validator accepts dir-team
  or neutral for non-structures). BuildingLogic.TEAM_OWNED_NAMES.
- mine, camp, outpost, blacksmith, lumbermill: team = "neutral",
  subtype = "backwood" (shipping-map convention, blacksmith/camp/lumbermill
  confirmed).

## Editor team-color preview

Unit.setup_team -> set_anim recolors sprites ONLY at runtime (blue ->
"default", red -> "red", neutral -> "neutral"); the building scenes ship
showing blue. BuildingLogic.apply_editor_team_visuals applies the same
mapping to the placed instance's AnimatedSprite2Ds (guarded by
sprite_frames.has_animation) so the editor shows the final color.
Preview-only overrides: runtime re-applies per actual team.

## What exists (verified 2026-11)

- Building scenes to palette: `unit/buildings/` — castle, barrack, tower,
  outpost, mine, church, lumbermill, blacksmith, camp (+ decoration/flag).
- Runtime contract (map/map_manager.gd `setup_buildings`): iterates EVERY
  child of `buildings` as a team, every child of that as a building, then
  `building.agent.set_state("lane", building.subtype)` and sorts by
  `building.team` into player/enemy/neutral lists. Buildings are units —
  they need the full unit script/scene, not a bare Node2D.
- Team structures (castle, barrack, tower) need `team` == their directory
  and `subtype` == a real lane name (WalkLane plans against it). Neutrals
  sit under a team directory but carry team="neutral" and subtype
  "backwood" or a lane (map_validator._check_building).
- A team without a castle breaks the win condition (validator error);
  blacksmith wants a `closest_tree` Marker2D child (validator warning).
- Building names must be unique per team (get_node first-match; validator
  warns on duplicates). The scaffold (map_scaffold.gd `_populate_team`)
  shows the established instantiate/set subtype/set team pattern and its
  name-escape gotcha ("name clashes with buildings/blue/castle/hud").
- The scaffold's scene positions live at `positions[building_name]`
  dictionaries — placement must instead come from clicks.

## Design sketch

1. **Pure logic first** (`building_logic.gd`, RefCounted, headless-testable
   like lane_logic.gd):
   - `place_target(map_root, team) -> Node` — resolves buildings/<team>,
     null-safe (map without that team dir must not crash; the dock errors).
   - `next_building_name(team_node, base_name) -> String` — "castle",
     then "castle_2", ... (validator duplicate rule; mirror
     LaneLogic.next_lane_name).
   - `apply_building_meta(building, team, lane_name)` — sets team/subtype
     per the team-structure vs neutral table above.
2. **Click -> world**: DONE via M1's lesson: the conversion was generalized
   to `LaneLogic.viewport_to_node_xform(node, viewport_canvas_xform)`
   (the lane call sites were updated; no wrapper kept), composed with the
   team node's global transform and snapped to the 64 grid. Do NOT use
   get_global_transform_with_canvas / canvas_transform (identity in the
   4.7 editor; see M1.md root cause).
3. **Plugin input**: a second mode next to lane drawing (`_placement_mode`
   + selected scene). Reuse the `_handles` gating; Escape exits; dock
   toggle stays in sync (copy _set_lane_mode's shape).
4. **Undo**: undo_redo action per placement — add_do add_child + set_owner
   + do_reference, add_undo remove_child + queue_free (same shape as
   _add_lane). PackedScene.pack() owner rules from M1's engine facts apply
   on save: the placed instance's own owner must survive.
5. **Dock UI**: palette as a grid of scene-name buttons + a blue/red team
   selector; log every placement like lane points do.
6. **Validator**: extend only if placement can produce states the current
   checks don't cover (e.g. warn when a building is outside map 'size';
   confirm the neutral-under-team-dir convention is still what placement
   emits). Do not loosen existing checks.

## Engine facts carried from M1 (keep)

- `const X = load(...)` illegal (use preload); FileDialog needs the root
