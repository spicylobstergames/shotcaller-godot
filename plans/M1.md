# M1 - Map editor plugin: finish lane-drawing coordinates

## Where we are (branch feature/map-editor-plugin, commit e19c9c1+)

The whole plugin works EXCEPT the final coordinate conversion of
lane-drawing clicks. Everything else is verified: scaffold (Phase 1),
validator, save/load roundtrip, generic map loader in map_manager, plugin
input forwarding via `_handles`.

**Symptom (user report, 4.7.2 editor):** clicks add points clustered near
map origin (0,0) regardless of camera; the blue overlay "moves with the
camera" instead of the world; the dock log shows plausible-but-wrong values
(e.g. clicked (342,928) -> added (320,960) — conversion was near-identity).

**Root cause (established, do not re-litigate):**
`_forward_canvas_gui_input` receives clicks in the 2D editor's VIEWPORT
(screen) space. The built-in Line2D/polygon editors convert with
`CanvasItemEditor::get_canvas_transform().affine_inverse().xform(pos)` —
an internal C++ singleton (see godotengine/godot 4.3
editor/plugins/abstract_polygon_2d_editor.cpp, forward_gui_input +
forward_canvas_draw_over_viewport). The GDScript temptation
`EditorInterface.get_editor_viewport_2d().canvas_transform` is NOT the
editor's pan/zoom transform in 4.7 (empirically near-identity; user trace
above proves it) — that was commit e19c9c1's failed attempt. Do not use it.

**Fix just committed (needs user verification):** use the target lane's own
`get_global_transform_with_canvas()` — item-local -> viewport-canvas space
via the same pipeline the renderer uses, so it equals
`CanvasItemEditor::get_canvas_transform() * lane.global_transform` and
tracks pan/zoom. Inverse gives lane-local directly (no to_local); same
transform is used for the overlay. See map_editor_plugin.gd
`_add_lane_point` / `_forward_canvas_draw_over_viewport`.

## If it still misbehaves, the diagnostic is already in the log

Mode-on and every click log raw click position AND
`xform.origin` (lane global-with-canvas origin). Decision table:
- Added point wrong, xform.origin ~ (0,0) while camera panned ->
  get_global_transform_with_canvas does NOT include the editor transform in
  this engine version; next option: walk up from the lane and compare
  `lane.get_viewport().canvas_transform` vs CanvasItemEditor's transform
  exposed some other way (check ClassDB for a getter; or read the 4.7.2
  source for where canvas_item_editor applies `transform` to rendering).
- Added point correct on screen but wrong values in the .tscn -> local/
  world axis mixup in lane_logic (unlikely; unit-tested).
- No "Added point" line at all -> forwarding broke again (check
  `_handles` is still implemented and the edited object is a BaseMap scene).

## Engine facts learned the hard way (keep)

- `_forward_canvas_gui_input` is only called for plugins implementing
  `_handles` (+ no-op `_edit`/`_make_visible`) that currently handle the
  edited object. `set_input_event_forwarding_always_enabled` is 3D-only.
- `EditorDock` is a native class in 4.7 — don't shadow it with a const.
- `EditorPlugin` overlay redraw method is `update_overlays()` (no
  `update_canvas`/`update_canvases` in 4.7).
- `const X = load(...)` is illegal (use `preload`); cross-script access to
  `const PackedVector2Array` members fails to compile (use static funcs).
- `PackedScene.pack()` only serializes nodes OWNED by the root; instanced
  sub-scene internals must keep their own owner (no owner flattening).
- Node API auto-dedupes sibling names; duplicate names only via .tscn text.
- FileDialog must be parented to the root viewport for popup() to work.
